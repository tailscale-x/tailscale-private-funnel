# Released v4.0.3 deployment — 20 October 2026

Subsequent update: the pending Voice ownership issue below was resolved by the [development hostname-isolation and gateway-cleanup fix](kubernetes-hostname-cleanup-20261020.md). This document retains the original v4.0.3 rollout observations.

## Artifact and scope

Released commit `a053d07bd38a7e2efe5059346f10950acfb71c1c`, native binaries downloaded from the GitHub release and verified against release checksums. Kubernetes image is pinned to `sha256:55ca6dad7a779d627a36e671ae02d379550790955a94865db7c048d8e34fc525`; operator OCI chart version is `4.0.3`.

Deployment targets:

- DLKN: PostgreSQL-backed control, Kubernetes gateway agent, three forwarders, operator.
- m090dev and m090prd: each gateway agent, three forwarders, operator.
- xvps: native public load balancer.
- Tiny and 5090: native Docker gateways.

5090 k3s was removed by the user and was not recreated. Its old Kubernetes gateway is not an active deployment target. No build ran on xvps or 5090.

## Persistence verification

- Control database was backed up before replacement. `main-material` Secret UID and all Secret data remained identical.
- All 11 DNS-ledger rows remained byte-for-byte equal after deployment, including remote record IDs and ownership.
- xvps, Tiny, and 5090 kept their existing native Tailscale device IDs and unchanged runtime configuration hashes.
- Kubernetes Pods use disposable identities by design. Logical gateway/forwarder IDs, applications, database, signing/encryption material, and DNS ownership were preserved.
- Native service backups include the previous unit, metadata, and state/data archives. Certificates were retained.

## Observed disruption and remaining checks

The public probe loop records TLS-verified requests to admissions API/public/SSO/eoffice, Harbor, Metube, and both LuongGia endpoints. Planned native restarts and gateway replacement caused failed samples; this was not a zero-downtime update.

After control replacement, its new host was auto-approved but initially absent from the existing edge netmap. Normal subsequent gateway registration caused the missing route to appear; no second edge restart, identity reset, ACL change, or artificial QA device was used. The edge then reached control directly over UDP.

This matches Tailscale's acknowledged missing Service-host map notification issue: [upstream report and cause](https://github.com/tailscale/tailscale/issues/19666#issuecomment-6153756034). v4.0.3 diagnostics expose this condition; they do not claim to repair the upstream map notification bug.

A concurrent Voice deployment attached `voice.troly.ai.vn` in DLKN while the hostname remained owned by the removed 5090 gateway. The resulting exact-ownership conflict rejected the whole DLKN Kubernetes snapshot. Admissions continued from retained state, while LuongGia lost its advertisements during normal forwarder replacement. The Voice deployment thread is detaching only its new HTTPRoute so unrelated snapshots can reconcile. No direct database ownership reassignment or unowned DNS mutation was performed.

## Final acceptance

At 15:45 ICT (08:45 UTC), every running component binary reported `v4.0.3`. Control and all three FunnelGateway CRs were Ready. DLKN's public Gateway and all seven attached HTTPRoutes reported `Programmed=True`. Every gateway and the public edge had fresh reports (1–15 seconds old at the database check).

After detaching the conflicting Voice HTTPRoute, both LuongGia listeners reopened and advertised as approved/ready. The existing edge selected the new host directly over UDP without an extra restart. All eight monitored public endpoints returned HTTP 200 with certificate verification enabled. The last failed sample was at 15:43:07 ICT; the final clean observation window lasted 144 seconds with 213 successful requests. This verifies current recovery, not long-term immunity to the upstream Service-map issue.

Final checks preserved all 11 DNS-ledger rows and all existing exposure IDs. Public IPv4 resolution for the eight monitored hostnames remained `160.191.243.219`. Native configuration hashes and device identities were unchanged. No ACL changes, hostname reassignment, or unowned DNS mutation was performed.

One m090prd replacement forwarder restarted once while the operator key-issuer endpoint was unavailable during its update, then became Ready. No reboot testing or deliberate external-API failure injection was performed in this deployment.

## Remaining Voice work

The Voice ownership handoff is a separate unresolved operation, not evidence that the removed 5090 backend is healthy. Its new HTTPRoute remains detached; its backend and PVC are managed by the Voice deployment thread.

Released v4.0.3 has no administrator RPC for releasing a stale Kubernetes application's hostname. Disabling the old node does not clear its hostname membership, and the delete-exposure RPC is limited to tailnet applications. No direct SQL reassignment was used. Reattaching Voice before a supported ownership release will block the whole Kubernetes snapshot again. This remaining isolation gap should be addressed separately.
