## Deployment

Updated the four operators and Kubernetes gateways in DLKN, m090dev, m090prd,
and 5090, including ten node-local forwarders. Control remains embedded and
PostgreSQL-backed in DLKN. Kubernetes workloads use the pinned release image.

Updated Tiny and 5090 native Docker gateways, and the xvps native public load
balancer, using the released Linux binary. All native services use embedded
Tailscale. Host-reused control remains explicitly unsupported and fails closed;
see [role and transport verification](../qa-tailscale-native-roles.md).

GitOps commit `b0a553b5afc2b9ef01246870e00ad5bcd8e7331a` records the release
image and chart. All six Funnel Argo applications returned to Synced/Healthy,
with reconciliation resumed and maintenance annotations removed.

Updates caused temporary 404 responses while disposable identities, assignment
leases, Service listeners, and load-balancer routes recovered. This was not a
zero-downtime rollout. Some forwarders retried bootstrap while their operator
endpoint was replacing; all Deployments and DaemonSets subsequently rolled out.

### Fresh-name DNS/ACME limitation

New disposable names in `dlkn.dev` and `troly.ai.vn` were added by control. Read-only Cloudflare
API inspection confirmed DNS-only A records with the correct public address.
However, Cloudflare's authoritative server returned `NXDOMAIN` over TCP with
`AA` set, and multiple public DNS-over-HTTPS resolvers returned `NXDOMAIN` too.
ACME therefore could not validate these fresh names. Waiting for the ledger and
an additional publication interval did not establish successful first-visit
issuance during this rollout. This is an unresolved API/authoritative-DNS
discrepancy; it is not claimed as a passing certificate-issuance check.

Existing public DNS/TLS remained healthy. No direct provider mutation was used
to work around the discrepancy. Streaming was also checked with a persisted
certificate and explicit address resolution, which distinguishes forwarding
behavior from new-name DNS publication.

### Released Docker forwarding

An isolated labeled HTTP fixture on a user-defined Docker network passed through
the released native Docker gateway and public load balancer using the persisted
certificate:

- HTTP/1.1 and HTTP/2 each delivered **1,050,018 bytes**, 128 SSE frames, and the
  final `[DONE]` frame.
- WebSocket echo completed.
- Host, query string, HTTP method, and POST body were preserved.
- Spoofed `Forwarded`, `X-Forwarded-*`, and `X-Real-IP` values were removed or
  replaced with trusted public-client/HTTPS values.
- Docker `PortBindings` was empty. The path used the reported container IP and
  port, without a relay or published-port forwarding hop.
- The certificate fingerprint was identical before and after release deployment.

### Cleanup

The fixture container and its network were removed. Authoritative Docker
inventory retired the fixture exposures, and control removed all five test DNS
records. Read-only Cloudflare inspection confirmed their absence. The final
ledger exactly matched the eleven baseline records and owners; all fixture
exposures were inactive. Temporary native probe executables were removed.

## Boundaries

The development rollout had already verified real host-reused Service forwarding,
direct Docker streaming, WebSockets, spoofed-header sanitization, role isolation,
and disposable forwarder replacement; its evidence is in the linked QA document.
The unsupported host-control path is excluded from this release's supported modes.
Public IPv6 WAN operation and active-active control are not acceptance claims.

Private receipts, credentials, database snapshots, and synthetic UI screenshots
remain outside the repository.
