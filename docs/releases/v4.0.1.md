# v4.0.1 — Tailscale-native component roles

This release replaces Funnel-specific enrollment and signatures with verified
Tailscale identity and installation-specific role authorization. It is a breaking
runtime/API change; update the installation policy and key issuer before deploying
matching control, load-balancer, gateway, and operator builds.

## Identity and authorization

- One installation OAuth issuer, restricted to `auth_keys` and its issuer tag,
  mints one-use keys for the five device roles it directly owns.
- Correctly tagged devices register automatically. Runtime roles do not grant
  human management access; hostname policy and DNS ownership still apply.
- Native embedded identities persist. Kubernetes Pods get fresh ephemeral
  identities while logical components, applications, database encryption material,
  DNS ownership, and Caddy certificates remain persistent.
- Control has a stable Tailscale Service endpoint instead of a disposable device IP.
- Service management uses a separate `services` + `devices:core:read` credential
  tagged with the control role, which owns both installation Service tags.
  Human-role lookup and public-endpoint discovery remain separate credentials.

## Direct Docker forwarding

Docker gateways dial the approved container IP and port directly. Relay containers,
relay images, and Docker-published forwarding ports are removed. Network selection,
deny patterns, backend validation, authoritative inventory retirement, streaming,
WebSockets, prefix rewrites, and ownership-scoped cleanup remain enforced.

## Kubernetes and native operations

- Disposable Kubernetes identities replace forwarder identity Secrets and remote
  identity restoration. Authenticated Pod bootstrap and assignment coordination
  remain; workloads never receive issuer OAuth credentials.
- Native load balancers and Docker/Tailnet gateways can use embedded Tailscale or
  an appropriately authorized host daemon. Borrowed identity and unrelated Serve
  configuration are preserved. Control requires embedded Tailscale.
- Control Service listeners preserve peer identity with mandatory PROXY v2 metadata;
  host-reused control fails closed because upstream tailscaled does not support
  PROXY v2 over a Unix backend. No HTTP-header or unprotected TCP fallback is used.
- Logical component/routing IDs remain distinct from Pod and device identities.
- An unchanged authorized instance can recover its lease after a control outage;
  replaced or explicitly stopped holders cannot reclaim an assignment.
- PostgreSQL control no longer attempts to create an unmounted SQLite directory.

## Deployment guidance

See [installation and role policy](../../README.md),
[installer workflow](../INSTALLER-WORKFLOW.md), and
[Kubernetes deployment](../KUBERNETES.md). Generated policy is a proposal: review
and apply it in Tailscale. Existing broad grants can weaken isolation.

No active-active control or zero-downtime guarantee is introduced. Back up matching
application data and encryption material before replacing infrastructure.

## Release validation correction

Fresh installer requests without an explicit version now default to the running
control release, rather than a hardcoded v2 release. Explicit version selection
remains available. The v4.0.0 publication run was stopped before artifacts were
published; its Git tag remains immutable.
