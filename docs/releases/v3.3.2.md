# v3.3.2 — Automatic Docker registration cleanup

Removing a Docker container or its Funnel forwarding labels now releases its registrations after a complete signed inventory confirms their removal. Policy-authorized Kubernetes routes can then claim those hostnames normally, without a special handoff operation.

## Safety and isolation

- Stopped containers retain registrations. Failed discovery, invalid labels, unreachable backends, and offline gateways do not release ownership.
- Signed, caller-scoped inventories use persistent revisions and replay protection.
- Exposure IDs and DNS ledger ownership survive normal Kubernetes reclamation.
- Retired entries in mixed old reports cannot block unrelated applications.
- Unused Tailscale Services are cleaned asynchronously, preserving shared references and gateway identities.
- SQLite and PostgreSQL retain retirement history and inventory state.

## Upgrade

Update control first, then Docker gateways. Preserve existing state/data directories, including the new inventory revision file. Older gateways cannot trigger automatic retirement until upgraded.

Ordinary removal can withdraw unused owned DNS before a destination becomes ready. This is not a zero-downtime transfer or a pending hostname reservation.

## Verification

The development build was deployed to DLKN control and Tiny's shared Docker gateway. Kubernetes automatically reclaimed all four university hostnames. All four HTTPRoutes reached `Programmed=True`; three rounds of DNS and certificate-verified HTTPS checks across those hosts, Harbor, and Metube passed (18/18).

Node identities, credentials, exposure IDs, ledger owners, and seven independent DNS records were preserved. Both Go suites, vet, PostgreSQL contracts, generated-asset checks, and image startup checks passed.
